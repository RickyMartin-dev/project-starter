A local memory and workflow layer for coding agents.

Project Starter gives coding agents a shared project contract, bounded access to prior work, repeatable checks, and a reviewed path for turning recurring experience into better project guidance.

Repo-wide source review · independent cold read · official ecosystem research · 2026-11-28

  • Markdown + Bash + Git
  • No service or model training
  • Memory stays reviewable
Verdict: The project delivers a careful, useful continuity and governance system. It does not make the underlying model learn or guarantee better work. Existing-repo setup and proof of improvement are the largest remaining gaps.

How the pieces connect

The agent reads one shared contract, uses a small command layer, then leaves evidence in files that a person or the next agent can inspect.

Memory

Plans, handoffs, lessons, and snapshots live as normal Markdown under docs/. Recall returns a small, sanitized set of lexical matches.

Verification

Shell checks, Git hooks, and read-only GitHub workflows protect the starter's own contract. An adopting app supplies its own test, build, and deploy checks.

Improvement

Friction and research can suggest narrow changes. A person reviews shared policy, permissions, and automation changes before promotion.

Use it with low overhead

For a fresh starter checkout, the routine path is a few shell commands. `start` writes ignored local state; durable project records are created only as work warrants them.

git clone https://github.com/RickyMartin-dev/project-starter.git my-project
cd my-project
./scripts/project start --task "Describe the first task"

  1. Orient

    Read AGENTS.md, then `.agent-state/session-context.md`. The latter contains up to five history matches; treat them as evidence and confirm current facts.

  2. Tailor once

    Replace the starter's project brief, command list, and architecture map with the product's truth. start detects common stack signals; it does not write those docs for you.

  3. Do only the needed process

    Plan larger work with ./scripts/project plan. Keep trivial changes direct. Use targeted prompts and skills only when their workflow matches.

  4. Verify the product and the layer

    Run the adopting app's documented checks, then ./scripts/project check. Run ./scripts/project release-check before pushing.

  5. Preserve learning

    Finish meaningful work with ./scripts/project finish --summary "...". It records a local snapshot and handoff; an optional archive needs an explicit local path.

Existing repository: there is no overlay installer today. Merge files with a diff, keep existing instructions, hooks, and CI, and do not import this repo's task history as the adopting project's memory. See the adoption guide.

The strongest fit is low-infrastructure project continuity with deliberate human review. The weak fit is “drop one thing into any repo and immediately prove it makes agents better.”

Gaps

These are the remaining gaps after the code and documentation fixes in this pass. They are based on repository inspection plus the official ecosystem sources linked below.

No safe one-command installer for an existing repo

The repository says “copy or merge,” but an adopter still has to reconcile AGENTS.md, provider settings, Git hooks, CI, and project memory by hand. A naive copier could overwrite existing authority or import this starter's history. I added a conflict-aware guide; a preview-first installer remains the clearest way to meet the “low setup” promise.

Next evidence: install into a fixture repo that already has instructions, hooks, and workflows; prove no pre-existing file or hook changes without an explicit choice.

No empirical measure that agents improve

The shell gates prove file contracts and workflow behavior. They do not compare agent task quality, retries, wall-clock time, or input-token use with and without the starter. The project-logic skill has prompt cases, but the repo check validates the CSV shape rather than running agent sessions.

Next evidence: a small matched task set with explicit outcome, process, cleanliness, and token/time checks. Start from the existing experiment system rather than adding a service.

Provider behavior is described more broadly than it is tested

The core Git hook setup now preserves active native hooks in normal checkouts and linked worktrees, but automated checks do not launch Codex, Claude Code, or Cursor to verify skill discovery, command routing, client hooks, or how each client loads the contract in a linked worktree. The project-logic skill has Codex/Claude copy parity checks; Cursor uses the shared commands and Impeccable files.

Next evidence: keep version-stamped, small discovery smoke checks for supported clients; clearly mark unsupported or unverified combinations.

Automatic periodic review depends on GitHub Actions

The weekly suggestion job is visible in an Actions run summary, but projects without GitHub Actions have no scheduler. They can run ./scripts/project suggest-upgrades manually; scheduled execution is intentionally not installed locally.

Decision: keep local scheduling opt-in. A launch agent, cron job, or hosted notification would add setup and authority that the core does not currently need.
